# M2 core review (keywhere-core)

Uncommitted `crates/keywhere-core` only: `KeyMaterial`, Vault save/conflict, `.plk`, generator, password history. `cargo test --release -p keywhere-core`: 19 passed, 0 failed.

## MUST-FIX

### 1. Conflict check does not cover the write

`save` (`crates/keywhere-core/src/lib.rs:342`) hashes the file, then `save_overwrite` (`lib.rs:357`) encrypts, fsyncs a temp, and reads the live file again only to copy it to `.ibak` (`lib.rs:364`). That read is never compared to `disk_hash`. A sync client, Password Safe, Gorilla, or a second Keywhere that lands during the backup fsync is replaced by `rename` (`lib.rs:374`). `disk_hash` is then set from the bytes we intended (`lib.rs:385`), not from a read-back.

Fix: hash `prev` and return `Error::Conflict` before writing a new `.ibak` or renaming. Re-read once more immediately before `rename`; on mismatch delete the temp and return `Conflict`, leaving the live file as it is. Set `disk_hash` from a post-rename read of `path`. The rename itself is still a window; hold the `.plk` across this function so two local writers cannot both pass the check. mtime is not a substitute for the late hash.

### 2. `.plk` release can delete a lock it does not own

`Drop` (`crates/keywhere-core/src/lock.rs:116`) reads the path and then `remove_file`s it. `take_over` (`lock.rs:83`) unlinks and recreates in that gap, so drop removes the new owner's file. A second `acquire` in this process (`lock.rs:71`) returns another `VaultLock` with the same identity, and either `Drop` unlinks while the other still believes it holds the lock. If `write_all` or `sync_all` fails (`lock.rs:65`), the error returns with no guard and an empty `.plk` that blocks everyone, including us.

Fix: one unlinker per path (a second acquire must not own a second `Drop`). Keep the lock fd open with `flock(LOCK_EX)` from a successful create until drop. Unlink only while that flock is held, and only if `fstat` of the fd matches `stat` of the path and the contents are still our identity. `take_over` takes the same flock before `remove_file`. On write or sync failure, unlink the file just created.

## SHOULD

- **Password Safe lock bytes.** Unix pwsafe writes `user@host:pid` as `wchar_t` and reads it back with `fread` of `wchar_t`. Windows writes UTF-16. We write UTF-8 (`lock.rs:65`). Peers still see a lock and open read-only, but `read_to_string` fails on their file, so the holder is empty and `is_stale` (`lock.rs:94`) is never true for a dead pwsafe pid. Accept UTF-8, UTF-16LE, and UTF-32LE. `stoi` accepts an unpadded pid. `with_extension("plk")` (`lock.rs:11`) maps `x.cfg` to `x.plk`; pwsafe appends, giving `x.cfg.plk`.
- **Synced `.plk`.** This is not a distributed lock. Both sides can `create_new` before the file syncs, and a remote delete races a local create. Other hosts correctly stay non-stale (`lock.rs:97`); the UI must still offer `take_over`. Gorilla writes no `.plk`. The content hash is what prevents a lost update across devices, which is why finding 1 matters.
- **History is safe to parse and easy to mis-write.** `history` (`lib.rs:182`) uses `str::get` and `char_indices`, so a hostile length, a short tail, or a non-UTF-8 field yields a short `Vec` and does not panic. `count` is at most 255. The length is Unicode scalars: that matches Linux pwsafe (UCS-4 `wchar_t`) and Gorilla's Tcl character count for BMP text. Windows pwsafe stores UTF-16 code units (format v3: "in TCHAR"). One emoji is one scalar and two `wchar_t`, so Windows pwsafe then consumes the next entry. `{:04x}` (`lib.rs:207`) prints five digits once a password exceeds 65535 scalars and desynchronizes every later entry; refuse that length instead of writing it. `set_history` always writes status `1` (`lib.rs:205`), which turns history back on after the user set `f` to `0` and stores a password they asked not to keep. Preserve `f`, and append only when it is `1`.
- **`encode` no longer enforces the iteration floor** (`psafe3.rs:291`). `Vault::decrypt` does (`lib.rs:260`), so the Vault path upgrades a file under 262144 before the next save. Reject a weaker `key.iterations` inside `encode` so `decode` plus `encode` cannot persist it.
- **`entropy_bits`** (`generator.rs:85`) is `length * log2(|alphabet|)` and ignores the "every class appears" rejection, so the displayed value is a slight overestimate. The sampler is not biased.

## OK-as-is

- **Keeping P′ and the salt is acceptable, and better than keeping the passphrase.** P′ is the password-equivalent for this salt only. The salt and `SHA-256(P′)` are already in the header, so a dump of P′ decrypts this vault and every later save that still uses this `KeyMaterial`, including ordinary `.ibak` copies. It does not open another vault. `change_password` and the iteration upgrade drop it via `Zeroizing`. The passphrase would keep working after that, and anywhere else it was reused. The salt is not extra secret; it is what lets a save write a header the same passphrase can open. K and L stay fresh per save and are not retained. Wipe P′ on lock. `mlock` is still the separate follow-up from the threat model.
- **Reusing the salt on ordinary saves matches Password Safe.** Format v3 §2.2 generates it at creation and pwsafe keeps it until a passphrase or iteration change. Readers only need the salt stored in the header. Fresh K, L, IV, and padding on every `encode` (`psafe3.rs:293`) is what stops an old K from opening the new file. A new salt from `KeyMaterial::derive` (new vault, passphrase change, or the unlock-time upgrade) is the right time to rotate. The upgrade stays in memory until a successful save, so a crash leaves the old file alone.
- **Generator draws are unbiased.** `uniform` (`generator.rs:97`) accepts only `v < floor((2^32-1)/n)*n`. That width is a multiple of `n`, so PIN, word, and alphabet indexes are uniform. It rejects a few more values than `2^32 % n` and does not skew. Random mode samples the full alphabet, then rejects until every selected class appears, which is uniform over that subset. The classes do not overlap. Passphrases sample the 1296 EFF words with replacement, and `entropy_bits` matches that model. No lookalike class is empty, and random length is at least 8 with at most 4 classes, so the loop cannot spin.
- **Save path around the race is sound:** same-directory temp, `create_new`, mode `0600`, fsync, `decode_with_key` verify, `.ibak` via rename, directory fsync, temp removed on error. Verifier and HMAC compares stay constant-time. Unknown fields still round-trip. Gorilla files with more than `2^24` iterations still fail at open; that cap is unchanged and is the DoS bound, not a new interop break.
